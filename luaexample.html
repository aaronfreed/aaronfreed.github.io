A Lua Shortcut

Normally, I’d simply tell you to apply the same heights, minus 2 WU, to each floor. And you can do that if you like. But using Lua can make this process a lot less tedious.

A Few Prefatory Caveats

First, though, I have a caveat:

If you don’t know what you’re doing, running Lua on your maps can easily mess them up!

To save yourself a tremendous amoung of heartache:

  1. Save your work before you modify it with Lua scripts.
  2. Before running any script, be sure you have a very good idea of what it will do.
    1. Corollary: If you run something and don’t have any idea what it did, revert to your last saved version.
  3. Test the results thoroughly.
  4. Have a good version control system in place in case you need to revert to an older version.

Also, while I’m thinking of it, Lua is not an acronym and thus should not be written in all caps. It is a word – namely, the Portuguese word for moon, cognate to the Latin and Spanish word luna. Lua (the language) originates from the Pontifical Catholic University, located in Rio de Janeiro, Brazil.

The Code

With those caveats aside, once you’ve saved your map, go into visual mode and press the key to enter the console, which is backslash (\) by default. Now type the following code, which will assign every polygon in the level a floor height of its ceiling height minus 2 WU (2048 IU). You must enter this code exactly as indicated – Lua is case-sensitive, and spaces can be syntactically important, so they should go exactly as placed here:

for p in Polygons() do p.floor.z = p.ceiling.z - 2 end

This would normally be written (and we can read it) as:

for p in Polygons() do
    p.floor.z = p.ceiling.z - 2
end

However, entering more than one line of code in the console is complicated at best.

Decoding the Code

A line-by-line explanation:

  1. for p in Polygons() do
    Iterates through every member of Polygons, using p as an alias for the polygon at that stage of the loop. This is Aleph One-specific syntax; I’ll review more traditional Lua syntax below. 
  2.     p.floor.z = p.ceiling.z - 2
    The floor height (p.floor.z) is assigned (=) the ceiling height (p.ceiling.z) minus 2 WU (- 2). 
  3. end
    Denotes the end of the for loop, telling Lua to jump to the next instance of Polygons and repeat the code within the body of the for loop, if there is one, or stop looping, if there isn’t. (In this case, line 2 is the entire loop body, but loops can get far more complicated.)

If you’ve entered this correctly, the floor heights will change instantly. If you see a syntax error, correct the syntax and try again. If you didn’t see a syntax error, exit visual mode whether or not the heights changed; if they didn’t change, reload the level and try again.

A Few Brief Digressions

Digression 1: Traditional Lua Syntax

More traditional Lua syntax with the same result as the above loop would look something like:

    for i = 0, #Polygons - 1 do
        Polygons[i].floor.z = Polygons[i].ceiling.z - 2
    end

On which I have the following notes:

  1. #Polygons denotes the Polygons table’s length.
  2. We start at 0 and subtract 1 from #Polygons because Aleph One uses zero-based indexing. Since Lua uses one-based indexing (well, nobody’s perfect), standard Lua tables would use for i = 1, #Polygons.
  3. Polygons[i] denotes the member of the Polygons table with index i.

I leave decoding the rest as an exercise for the reader, with only the final note that i stands for iterator.

Digression 2: repeat…until

The following code also accomplishes the exact same thing, incidentally:

local i = 0
repeat
    Polygons[i].floor.z = Polygons[i].ceiling.z - 2
    i = i + 1
until i >= #Polygons

I’d add the following line to the above script, for reasons I’ll explain below:

assert(i == #Polygons,"Logic error: i ~= #Polygons after repeat...until loop")

Some explanations:

  1. local restricts the variable’s scope; its contents will be removed from memory after the current code level finishes executing. It’s good practice to restrict variable scope to local unless it’s strictly necessary not to – not only it is better for memory usage, but access to local variables is faster as well.

  2. >= is Lua’s “greater than or equal” operator. If we haven’t made logic errors, ==, the comparison operator, would be logically equivalent here. == returns true if two values are equal and false otherwise; it’s not the same thing as =. Remember this – I never do.⁽¹⁾ However, avoiding an infinite loop and throwing an assertion failure if the values aren’t equal at the end of the loop is better programming practice.
  3. The assert line helps detect logic errors. If i == #Polygons evaluates to false at the end of our loop, then we very likely skipped not just our final polygon, but others as well. That’s bad, mkay?

    Thus, if the first parameter of assert doesn’t evaluate to true, we want our script to immediately halt execution and tell us, “You done messed up, A. A. Ron!”

    …Sorry; the actual error it will display is its second parameter, which in this case is:

    Logic error: i ~= #Polygons after repeat...until loop

    Halting execution and displaying an error here is vastly preferable to letting logic errors living undetected, wreaking unknown havoc on our maps for untold amounts of time. It’s also preferable to an infinite loop, since it tells us exactly what went wrong and where to look for it. (The dialog box will give us a line number; the above error message reminds us to start searching for our error in the loop above that line. It’s ideal to keep assert error messages terse, but helpful.)

  4. " denotes a string literal; the characters enclosed between two " are usually the string’s contents, with exceptions for characters preceded by \. In particular, to get a value of " within a string, we’d have to use \". To get a backslash, we’d use \\. To get two backslashes in a row, we’d use \\\\. And so on. These can get complicated to parse; programs like Microsoft Visual Studio Code or Notepad++ can help.
  5. repeat…until should be mostly self-explanatory, so I’ll just point out that its body will always execute at least once, regardless of whether i >= #Polygons evaluates to true or not. If we want code that will only execute if the condition is true, we can use a while loop, explained in Digression 3.
  6. The for loop handles much of this automatically, reduces (but doesn’t eliminate) our need to worry about skipping values, and is probably more legible to boot; using them where possible is therefore good practice.

Digression 3: while

The following code is logically equivalent to the repeat loop in Digression 2.

local i = 0
while i < #Polygons do
    Polygons[i].floor.z = Polygons[i].ceiling.z - 2
    i = i + 1
end
assert(i == #Polygons,"Logic error: i ~= #Polygons after while loop")
  1. Note that we had to reverse the condition here: repeat…until only stops executing when its ending condition is false, while while only executes if its opening condition is true.
  2. Also, as noted above, repeat always executes at least once and only evalutes its condition at the end of the loop, whereas while evaluates its starting condition before it runs even once.
  3. Thinking of the interpreter evaluating a condition where it appears in the code can be a helpful mnemonic for which loop type is which. Since a while loop’s condition goes before its body, the interpreter must evaluate the condition before it can run the code within the loop even once; since the repeat condition appears after the loop body, the interpreter can only evaluate the condition after the loop body has run.
  4. As written, the only way the while loop will evaluate to false on its first iteration is if #Polygons is 0 – in which case, our map wouldn’t even have loaded!
  5. ~=, Lua’s “not equal to” operator, would be logically equivalent to < in the while comparison if and only if we didn’t make any logic errors. However, as with our above repeat example, I think getting an assertion failure if we did make a logic error is vastly preferable to getting an infinite loop (much less to letting the logic error live on, undetected, for untold amounts of time).
